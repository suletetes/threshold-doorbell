# Audit-findings remediation for threshold-doorbell (v1)

This branch resolves the 15 findings catalogued in `CODEBASE_AUDIT.md` (2 High, 6 Medium, 7 Low) in 16 atomic, single-author commits. The two High items get real code fixes with regression tests: `authenticateWs` now consults the post-erasure deny-list on both WebSocket routes (H-1), and the Android manifest gains a `threshold://` VIEW/BROWSABLE intent-filter plus a tested deep-link parser and `/oauth/exchange` contract (H-2). The Mediums split between code (service-layer size caps, bounded readiness probes, `webhook_ack_ms` instrumentation) and deliberate spec amendments (route schemas stay service-layer by choice; cross-instance ASR caps deferred). The Lows are mostly documentation of invariants already true in code, plus one real fix (L-4 forces refresh on an unparseable `expiresAt`).

Watch for: whether H-1 regresses the Origin/close-code guards it wraps (**confirmed** it does not); whether removing the `err.validation` branch orphans the `schema_validation_failure` metric (**confirmed** no metric is lost because the branch was unreachable); and whether the deferred/documented-only Lows actually needed code (**confirmed** they are honestly scoped, with H-2's README correction being the most important honesty fix).

I installed Flutter 3.38.10 (matching CI) and ran every suite on this branch: backend `typecheck`/`lint`/`test` (288 passing), `flutter analyze --fatal-infos` clean plus `flutter test` on the app (680) and the package (50). All green.

**Verdict**: APPROVED

## High-level view

H-1 is closed correctly on both live paths. `authenticateWs` became async and now returns null when `sessionInvalidation.isRevoked(sub, iat)` is true, after the Origin check and `verifySession` - so the MED-34 Origin allowlist and the token-source rules it already enforced still gate first, and both handlers keep their existing 4401 close path. The regression test erases via the real `DELETE /me/data` and asserts both `/signaling` and `/asr/stream` close 4401, plus a no-over-revocation case where a post-cutoff session still connects.

The M-1 decision to delete the dead `err.validation` branch and amend the design is sound. Adding Fastify body schemas would run validation before the `requireSession` preHandler and surface a 400 ahead of the 401, breaking the auth-first contract; the design now states this explicitly. No metric is lost: that branch could never fire because no route declares a schema, and genuine request-shape failures already return the `schema` (400) envelope through the service layer.

M-2's caps (visitorText <= 4096, turns <= 500, turn.text <= 2048) sit well below the 64 KiB body limit and above any legitimate payload, and reject with the uniform 400 envelope before the oversized data reaches Bedrock or storage.

H-2 is a genuine, honestly-scoped fix. The manifest filter matches the server contract (`scheme=threshold`, `host=auth`), the pure parser and the `/oauth/exchange` client are fully unit-tested, and `ProductionAuthPort.completeFromDeepLink` drives them while `reauthenticate` still fails closed for the device-bound browser/listener step. The README and design §12 now say sign-in is "not yet end-to-end on device," correcting the prior overstatement rather than inflating the fix.

L-6 is documentation plus overlap tests, and the "conservatively safe" conclusion holds: `maskedFraction` clamps to 1 and can only over-estimate coverage (stricter masking), and `maskBeforeDetection` subtracts zones into disjoint, zone-free strips so no masked pixel survives even when zones overlap. The new tests check this against an independently computed exact union.

The documentation-only resolutions (L-1, L-2, L-3, L-5, M-3) each record an invariant or a deferral that is genuinely a design choice rather than a latent bug: TLS-at-edge keying, the broad `.amazonaws.com` thumbnail suffix guarded by HMAC + HTTPS, the assumed Ring signing contract, `__unmapped__` retention bounded by the 7-day TTL, and the per-process cap that needs a shared store only once real adapters land. None requires a code change today.

Commit hygiene is clean: 16 commits, all authored by Suleiman, no AI/co-author trailers, no em/en dashes in messages or added source. The preserved security strengths (PKCE, HKDF, envelope crypto, constant-time compares, recursive log redaction, fail-closed boot, dash lint) are untouched by this diff.

### H-1: post-erasure deny-list now enforced on `/signaling` and `/asr/stream`

The HTTP guard (`requireSession`) ran `verifySession` and then `sessionInvalidation.isRevoked(sub, iat)`; the two WS routes went through `authenticateWs`, which only did the Origin check and `verifySession`. A bearer still inside its 30-minute absolute window could therefore open a live Ring signaling session and a Transcribe-billing ASR relay after the user asked for erasure. The fix makes `authenticateWs` async and adds the `isRevoked` consult after `verifySession`, returning null when revoked; both handlers now `await` it and pass `app.container.sessionInvalidation`.

The ordering is the important detail and it is correct: Origin allowlist (MED-34) is still checked first and short-circuits to null, `verifySession` (which enforces the token-source rules, HIGH-22) runs second, and the deny-list is consulted only on an otherwise-valid claim. Nothing in the close-code path changed - both routes still emit a typed `unauthorized` error frame and close 4401 when `authenticateWs` returns null, so a revoked bearer is indistinguishable from any other auth failure to the client, which is what the unified recovery flow expects.

The regression test is meaningful and would fail if the fix were reverted. It issues a pre-cutoff session, drives revocation two ways (direct `revokeSessionsIssuedBefore` and the real `DELETE /me/data` -> `eraseAll` path), and asserts both `/signaling` and `/asr/stream` close with their `unauthorized` code and that no signaling session was opened. It also includes a no-over-revocation case: a session issued *after* the cutoff still authenticates and completes an offer/answer, which guards against a fix that simply revoked everything.

### M-1: dead validation branch removed, spec amended to auth-first service-layer validation

```ts
// before: unreachable because no route declares a Fastify schema
if ((err as { validation?: unknown }).validation) {
  container.metrics.increment('schema_validation_failure');
  ...
}
```

No route sets a `schema:` option, so Fastify never produces an `err.validation`, so this branch was dead. The remediation deletes it and amends design §9 to state that validation is service-layer by choice, with the rationale that a route-level body schema validates *before* the `requireSession` preHandler and would leak a 400 ahead of the 401 that the auth-first contract requires. This is the correct call: the alternative (adding schemas) would reorder the 401/400 precedence that the HTTP suite asserts.

The `schema_validation_failure` metric is not orphaned in a way that matters - it was never reachable through this branch. Genuine malformed input is still rejected: the service layer throws `errors.schema()` (the 400 `schema` envelope) for bad field types/shapes, and the framework-level body guard (malformed JSON, oversized body, unsupported media type) still routes through the generic 4xx `schema` branch below. The one true consequence is that the counter named `schema_validation_failure` is no longer incremented anywhere; if observability depends on that specific counter it is now always zero, but that is consistent with the amended design and not a regression introduced by this change.

### M-2: per-field size caps below the body limit

`visitorText` is capped at 4096 chars before it can reach the Bedrock prompt path, `turns` at 500 items, and each `turn.text` at 2048 chars, all returning the uniform 400 `schema` envelope. The caps are applied in an order that preserves existing error precedence: `visitorText.length` is checked after the string-type guard (so a non-string still produces the type error first), and the `turns` count is checked before `.map(parseTurn)` so a pathological array is rejected before any per-turn work. The ceilings sit above any legitimate doorbell utterance or short conversation and below the 64 KiB body limit, so they bound abuse without rejecting real payloads.

### H-2: Android deep-link receiver, tested parser, and exchange contract

The manifest adds a second intent-filter - `VIEW` + `DEFAULT` + `BROWSABLE` with `android:scheme="threshold" android:host="auth"` - matching the backend's `threshold://auth/complete` redirect. `auth_deep_link.dart` is new and pure: `parseAuthDeepLink` returns a sealed `AuthDeepLinkCode | AuthDeepLinkError | AuthDeepLinkInvalid`, rejecting a foreign scheme or host, preferring a non-empty `code` over an `error`, and treating an empty code as invalid. `BackendAuthExchangeClient.exchange` posts `{code}` to `/oauth/exchange` and returns `verified` only on a 200 carrying a non-empty string `session`; a non-200, a non-JSON body, a missing session, an empty code, or a transport throw all map to `failed` - fail-closed, so a session never resumes on an ambiguous outcome (HIGH-09).

`ProductionAuthPort.completeFromDeepLink` wires these together and is covered end to end, while `reauthenticate` still throws `DeviceBindingUnavailable` because launching the browser and listening for the returning link are device/network bound. The split is honest: the server-side one-time-code handoff now has a real, tested client half instead of being orphaned, and the parts that genuinely cannot run headless remain deferred. The test suite exercises every parser branch, every exchange outcome, and the deferred-reauthenticate case.

The honesty of the surrounding docs is the part worth calling out. The README previously implied OAuth sign-in was built; it now states sign-in is "not yet end-to-end on device" and names exactly what remains (the live link listener and HTTPS client via `ProductionAuthPort`). Design §12 lists the same deferral with a date. The fix is described as what it is, not more.

### L-6: overlapping privacy zones cannot under-mask

Two independent claims, both verified against the code. First, `maskedFraction` sums per-zone intersection areas and returns `f > 1 ? 1 : f`, so overlapping zones can only inflate the estimate up to the clamp - never below true coverage. Since `isAdmissibleRegion` admits only when the fraction is *below* threshold and `admitDetection` additionally rejects any region whose center lies in any zone, an over-estimate can only discard more detections. Second, `maskBeforeDetection` subtracts each zone via `_subtract`, which returns up to four strips (top/bottom full-width outside the overlap band, left/right confined to the band) that are mutually disjoint and all outside the zone; iterating keeps every remaining region disjoint from every removed zone, so no masked pixel survives even with overlapping inputs.

The new tests substantiate this rather than restating the prose: they place a detection inside the overlap and assert it is discarded at any threshold with `maskedFraction == 1`, check a straddling region stays within `[exactUnion, 1]` using an independently computed union, and assert the `maskBeforeDetection` output has no region intersecting any zone, no two output rectangles intersecting each other, and a total remaining area of exactly 0.72 for the chosen overlapping pair.

### Mediums wired with real tests (M-4, M-6) and L-4

`runReadinessChecks` now wraps each dependency probe in `timedCheck`, racing it against a 1000 ms timeout, so a hung real adapter yields `ok:false` (503) instead of hanging `/ready`; the config check stays synchronous. The test injects a `tokenStore.get` that rejects and asserts `/ready` returns 503 with the `tokenStore` check `ok:false` - it would fail if the probe swallowed the error or reported ready. M-6 records `webhook_ack_ms` on the happy path right before the 200 ack (not the async push), and intentionally skips 401/400 short-circuits since those are not acknowledged deliveries; the test signs a valid webhook and asserts the latency summary count is >= 1. L-4 changes `nearExpiry` to `mustRefresh = !Number.isFinite(expiresMs) || expiresMs - now <= REFRESH_SKEW_MS`, so a corrupt `expiresAt` forces a refresh instead of vending a possibly-expired token; the test persists `expiresAt: 'not-a-date'` and asserts exactly one refresh invocation and a fresh token.

### Documentation-only resolutions (L-1, L-2, L-3, L-5, M-3, M-5)

Each records an invariant or deferral rather than papering over a bug. L-1 documents that `secure`/HSTS keyed on `env !== 'local'` relies on the TLS-at-edge deployment invariant and that deriving from `request.protocol` would wrongly drop the flag behind a terminating proxy - with the `x-forwarded-proto` fallback written down for a future topology. L-2 keeps `.amazonaws.com` but records that it must be narrowed to the real Ring bucket before go-live, acceptable today only because the source is HMAC-authenticated and HTTPS-filtered. L-3 writes the assumed Ring signing contract into the webhook route so a mismatch is diagnosable before launch. L-5 documents that `__unmapped__` events are bounded by the 7-day TTL and not retroactively re-attributed on device mapping, with the reason (no `EventStorePort` scan-by-deviceId) and the devices.ts mapping point annotated. M-3 records the per-process cap limitation and the shared-store remedy in design §12. M-5 fills `.env.example` with every config var `config.ts` reads (`WS_ALLOWED_ORIGINS`, the HMAC-rotation list, rate-limit and ASR knobs, body limit), which the `assertStrongSecret` boot guard already backstops against weak secrets.
