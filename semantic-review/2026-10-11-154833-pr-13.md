# Audit-remediation PR #13 ("Fix/audit remediation")

This reviews PR #13 by suletetes against `origin/main`: 59 commits, 251 files, +11,833 / -3,624. The PR is a
remediation pass over the findings in `semantic-review/2026-09-19-002908-pr-threshold-audit.md` and a separate
`CRIT/HIGH/MED/LOW/NIT` audit whose IDs are cited in nearly every commit message. The backend remediations are
the headline: the cross-resident `/events` leak that was the prior audit's P1 is genuinely closed, the
staging-boot-on-fixtures gap fails closed, and the OAuth/PKCE, webhook, signaling, and ASR hardening read as
real, correct fixes rather than symptom suppression. The test-strengthening commit converts vacuous assertions
into behavioral ones instead of gutting them. The problems are at the edges: the PR ships with **no
description, test plan, or risk notes** for an 11.8k-line security-sensitive change, and **every CI check is
reported red** on the head commit.

Watch for: (1) the PR has no body at all — no summary, no test plan, no per-finding evidence in the PR itself
(confirmed); for a change this large and this security-sensitive that is a review-quality defect on its own.
(2) All CI jobs are reported FAILED on the head commit except GitGuardian — backend vitest on node 20 and 22,
the flutter_ring_captions package, the secret scan, the app job, and the android apk/permission job
(confirmed from CI status); the job logs 404 and the failing-steps lists are empty, so whether these are real
regressions or environmental could not be established from CI alone, and the suites could not be reproduced
locally because `npm`, `dart`, and `flutter` are not on PATH and the backend has no `node_modules`
(confirmed). (3) The new `app` CI gate runs `flutter analyze --fatal-infos`, which the previous CI config
removed with a comment that it "crashes in the sandbox analysis server" — re-adding it as a hard gate is a
likely source of a red `app`/`packages` job (likely). (4) The android job asserts manifest permissions on a
**debug** APK, which does not exercise the R8/resource-shrinking release path that the HIGH-13 finding was
actually about (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The backend security remediations are the strong core of this PR and they hold up under reading. The prior
audit's cross-resident event leak is fixed at the data layer, not papered over: `EventStorePort.listOrdered`
now takes `residentSub`, `MemoryEventStore` filters by it, the webhook resolves the owning resident
server-side from the device→account mapping and quarantines unmapped devices under an explicit marker, and the
route derives `residentSub` from the verified session. The container fails closed when a non-fixture
environment boots without real adapters, and `loadConfig` rejects unknown envs, bad ports, and insecure
default/short secrets outside local/test. OAuth keeps the PKCE verifier server-side keyed by a nonce, binds
state to the browser with an `H(nonce)` cookie, mints a single-use app code for the native handoff, and
derives identity from the exchange result rather than the token string. WebSocket auth refuses the token in
the URL query and enforces an Origin allowlist. The ASR relay bounds session count, duration, open time, and
pending-frame buffer, and clears the replay buffer after a replay — the exact P2 nit the prior audit raised.

The test changes are good-faith strengthening. The "make vacuous tests assert real behavior" commit replaces
constant-equality checks with behavioral ones (ASR egress asserts processed-vs-transmitted, Privacy-Mode reply
asserts Bedrock is never invoked by leaving it in OK mode, the refresh-metric test seeds a token and exercises
the success branch, the logger test asserts the level actually silences output), and the backend `waitFor`
helper now throws on timeout instead of returning silently — which makes previously-passing timing assertions
able to fail. Nothing here reads as an assertion weakened to make CI green.

The process around the PR is where it falls down. There is no PR description, so the 59 commits and their
finding IDs are the only record of intent, and a reviewer has to reconstruct the test plan from the diff. And
the entire CI matrix is red on the head commit while the logs are unavailable, which for an "audit
remediation" PR is a contradiction that must be resolved before merge regardless of whether the cause is a
real regression or the sandbox runner.

The CI rewrite itself is mostly a security improvement — actions pinned to full SHAs with tag comments, job
timeouts, a gitleaks secret scan over full history, a production-only `npm audit` gate, and a node 20/22
matrix. Two of its new gates are plausible causes of the red status rather than genuine source defects:
`flutter analyze --fatal-infos` (previously removed as sandbox-crashing) and the android debug-APK permission
assertion that does not prove the release manifest.

### The cross-resident event leak is closed at the data layer

The prior audit's top finding was that `/events` returned every resident's door events because the event store
had no resident dimension. This PR fixes it in the three places the audit named. `EventStorePort.listOrdered`
now takes `(residentSub, since?)`; `MemoryEventStore.listOrdered` filters `e.residentSub === residentSub`
before ordering, so another resident's rows are structurally unreachable even though the idempotency map stays
globally keyed by `requestId`. The write path resolves the owner server-side: `WebhookService.record` calls
`resolveResident(deviceId)` and stamps the result on the event, and an unmapped device is quarantined under an
explicit `__unmapped__` marker rather than stored under `''` (so it is never orphaned and never pushed). The
route derives `residentSub` from `request.session!.sub`, never from the body.

```
POST /webhook  -> resolveResident(deviceId) -> event.residentSub stamped
GET  /events   -> listOrdered(session.sub)  -> only this resident's rows
```

Residual: the per-resident scoping lives in the fixture store, and the real DynamoDB adapter is deferred — the
guarantee is only as strong as the eventual adapter keying the table by resident.

### Boot fails closed; config validates and fails fast

`buildContainer` refuses to boot any env outside `{local, demo, test}` unless every real-adapter port is
supplied via overrides, throwing a message naming the missing ports (CRIT-02): a staging boot cannot silently
fall back to in-memory stores. `loadConfig` rejects an unknown `THRESHOLD_ENV`, a non-integer or out-of-range
`PORT`, and — outside local/test — any secret still at its insecure default or shorter than 32 chars. Confirm
`test` is never a deployable target, because the secret-strength assertion is skipped for both `local` and
`test`.

### OAuth/PKCE, state binding, and the native handoff

The OAuth flow addresses the prior audit's token-derived-identity concern directly. `residentSub` comes from
`tokens.residentSub` on the exchange result (`RingAuthResult extends OAuthTokens` with an explicit identity
field), with a comment that it is never parsed from the access-token string — the collision the prior audit
reproduced in `deriveResidentSub` is gone from the live path. The PKCE verifier is held server-side in
`oauthTxnStore` keyed by a random nonce and taken single-use on callback; the front-channel `state` carries
only the nonce, signed with a purpose-separated key and type-tagged `oauth_state`; and an `H(nonce)` HttpOnly
`SameSite=Lax` cookie binds the state to the browser, compared in constant time. The native app never receives
the session in the deep link directly — the callback mints a one-time `appCode` (2-minute TTL) and the app
exchanges it over HTTPS at `POST /oauth/exchange`. Cookies are `secure` whenever env is not local. A provider
error redirects to the deep link with `?error=` instead of stranding the user on a raw 400.

### Signaling: device authorization, single session, and slot release

`/signaling` authenticates the WS upgrade through `authenticateWs` (Origin allowlist + session from
subprotocol/cookie/Bearer, never the URL query), then enforces that the resident owns the device via the
server-side `deviceAccountStore.resolve(deviceId) === residentSub` check (HIGH-20) — an unmapped or foreign
device is closed 4401 without touching any incumbent session. The single-session invariant (FR-4.7) rejects a
second concurrent attempt with 4409 and explicitly leaves the incumbent alone. The slot-release logic handles
the mid-handshake disconnect the prior work flagged: ownership is marked before the `open` await, and the
close handler awaits the in-flight open before releasing so a socket that drops during the handshake still
frees the Ring session. The per-resident single-session state is a per-process map, correct for the fixture
but not a cross-instance guarantee.

### ASR relay bounds and the replay-buffer clear

The ASR relay closes the specific P2 nit from the prior audit: `reconnect()` replays at most the last 2s of
buffered audio and then calls `this.buffer.clear()` so the same audio is never replayed twice on a subsequent
reconnect, with a comment citing the finding. HIGH-22 resource guards are comprehensive — a per-resident
concurrent-session cap with slot accounting, a hard session-duration timeout, an open timeout that races the
upstream connect, and a bounded pending-frame buffer that fails the session rather than growing memory while
the stream opens. Frames are serialized through a promise queue so a `start` fully opens before any following
audio frame is processed, and `disposed` is re-checked after every await so a socket that closes mid-open
closes the freshly opened stream.

### Test changes strengthen assertions rather than weaken them

The "make vacuous tests assert real behavior" commit (8bdb397) is the one the briefing flagged for scrutiny,
and it holds up. The backend `waitFor` helper previously returned silently on timeout, which made every
`waitFor`-based assertion pass even when the awaited server effect never happened; it now throws with a
message, so a regression that stops releasing a session fails loudly. The Privacy-Mode reply test used to set
Bedrock to error mode (so a wrongly-routed request still returned the safe set via fallback and passed) — it
now leaves Bedrock OK and asserts `suggestInvocations === 0`, which can actually fail if Privacy Mode ever
calls Bedrock. The refresh-metric test previously branched on status and asserted 0 when the resident had no
token (never exercising the increment); it now seeds a valid token and asserts `200` + `counter === 1`. The
logger test replaced a `typeof log.info === 'function'` smoke check with capturing output and asserting that
`silent` emits nothing and `info` emits the message. On the app side the new gates (`FakeReplyPort.playbackGate`,
`FakeSessionPort.connectGate`) exist only to hold the controller in a named state long enough to assert the
rendered UI; they are test seams, not production behavior, and the composition-root test now pumps
`ThresholdApp` with the real production adapters and asserts answering the door fails closed to a visible,
dash-free error panel. These are real strengthenings.

### CI rewrite: mostly hardening, two gates worth confirming

The workflow change is largely a security improvement and should be credited: third- and first-party actions
are pinned to full commit SHAs with the tag in a trailing comment, every job has a timeout, a gitleaks job
scans the full history (`fetch-depth: 0`) and fails on any leak, a production-only `npm audit --omit=dev
--audit-level=high` gates advisories without blocking on dev-only ones, and the backend runs on a node 20/22
matrix. Two new gates are the plausible explanation for the red status rather than source regressions. First,
the `app` and `packages` jobs now run `flutter analyze --fatal-infos`; the previous CI config removed analyze
with an explicit comment that it "crashes in the sandbox analysis server," and re-adding it as a fatal gate
reintroduces exactly that risk. Second, the android job runs `flutter build apk --debug` and then asserts
RECORD_AUDIO/INTERNET on the debug APK — but HIGH-13 was about those permissions surviving the shrunk release
build after the ML Kit plugins were removed, and a debug build does not run R8 or resource shrinking, so the
assertion does not actually lock in the release-manifest guarantee it cites (CRIT-09, HIGH-12, MED-16, MED-19
in the step comment). The release-signing fail-closed in `build.gradle.kts` is correctly scoped to
`package*Release` tasks and so does not fire on the debug build, which is consistent.

### What could not be verified

The backend suites are the highest-risk area and the most likely to be runnable, but this environment has no
`npm`/`npx`/`corepack` and the backend has no installed `node_modules`, so vitest, `tsc` typecheck, and eslint
could not be run; `dart`/`flutter` are also absent, so the app and package suites could not be run. The CI job
logs return 404 and the failing-steps lists are empty. The backend, app, and CI assessments above are
therefore static reading of the diff only, and the red CI status is reported but not independently
reproduced — this is called out so the backend is not mistaken for test-verified by this review.
